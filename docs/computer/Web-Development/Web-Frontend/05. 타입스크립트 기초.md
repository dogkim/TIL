## 비동기 처리 — Promise, `.then()`, `async/await`

서버 요청처럼 시간이 걸리는 작업의 결과를 나중에 받기 위한 문법들. 셋 다 결국 같은 걸 하는데 표기법이 다르다.

- **Promise**: "지금 당장은 값이 없지만 나중에 채워질 상자". `supabase.auth.getSession()` 같은 함수가 돌려주는 게 바로 이거.
- **`.then(콜백함수)`**: Promise 안에 값이 채워지면 그 콜백을 실행하라고 예약해두는 방식.
  ```ts
  supabase.auth.getSession().then(({ data, error }) => {
    console.log(data, error);
  });
  ```
- **`async/await`**: 위와 똑같은 동작을 "위에서 아래로 순서대로 읽히게" 쓰는 문법.
  ```ts
  async function checkSession() {
    const { data, error } = await supabase.auth.getSession();
    console.log(data, error);
  }
  ```
  - `async`: 함수 앞에 붙이는 표시. 이 함수의 리턴값을 자동으로 Promise로 감싸고, 내부에서 `await`를 쓸 수 있게 허용한다.
  - `await`: "이 줄에서 응답 올 때까지 기다렸다가 다음 줄로 넘어가라."
  - `.then()`이 여러 번 이어지면 콜백이 중첩되어(`.then(() => { .then(() => {...}) })`) 오른쪽으로 계속 밀려나는데, `async/await`는 그런 중첩 없이 평범한 순차 코드처럼 읽힌다. 그래서 실무에서 표준으로 씀.

## 구조분해할당(Destructuring)과 Rest 문법(`...`)

함수는 값을 하나만 return할 수 있다(JS/TS엔 여러 값을 동시에 return하는 문법이 없음). 그래서 여러 값을 같이 돌려주고 싶으면 객체 하나로 묶어서 return한다 — Supabase API들이 `{ data, error }` 형태로 돌려주는 이유.

```ts
function getSession() {
  return { data: {...}, error: null }; // 객체 하나로 묶어서 return
}

const { data, error } = getSession(); // 구조분해할당으로 각각 변수로 꺼냄
```

구조분해할당 없이 쓰면 매번 `response.data`, `response.error`처럼 접두어를 붙여야 하는데, 구조분해할당을 쓰면 그냥 `data`, `error`로 바로 쓸 수 있다.

**Rest 문법(`...`)**은 "지정한 것들 빼고 나머지 전부를 새 객체로 묶어라"는 뜻:

```ts
const input = { email: 'a@b.com', password: '1234', nickname: '도균', gender: 'male' };

const { email, password, ...profile } = input;
// email = 'a@b.com'
// password = '1234'
// profile = { nickname: '도균', gender: 'male' }  ← 나머지가 새 객체로 묶임
```

## 스코프(유효범위)

`const`/`let`로 선언된 변수는 **자기가 선언된 가장 가까운 중괄호 `{ }` 블록 안에서만** 존재한다(블록 스코프). 함수, `if`, `for` 전부 각자 독립된 공간을 가지므로, 함수 밖에서 그 함수 안의 지역 변수에 접근할 수 없다. 서로 다른 함수의 변수가 실수로 충돌하지 않게 해주는 안전장치.

## `type` — 데이터 모양을 미리 정의

C/C++의 `struct`와 비슷한 역할("이런 필드를 가진 데이터 뭉치"를 선언)이지만 중요한 차이가 있다:

- **런타임에 완전히 사라짐**: `type`은 컴파일(JS로 변환)될 때 삭제된다. 실행되는 코드엔 타입 정보가 안 남고, 오직 개발 중 에디터/컴파일러 체크용으로만 존재 — 그래서 실행 속도에 영향 없음.
- **Union 타입 가능**: `gender: 'male' | 'female' | null`처럼 "이 값은 반드시 이 중 하나"라는 제약을 표현할 수 있다. struct로는 불가능.

```ts
export type User = {
  id: string;
  nickname: string;
  gender: 'male' | 'female' | null;
  createdAt: string;
};
```

### `Omit`, `Pick` — 기존 타입을 가공해서 새 타입 만들기

필드 목록을 매번 다시 타이핑하지 않고, 기존 타입에서 일부를 빼거나(`Omit`) 골라서(`Pick`) 새 타입을 만들 수 있다.

```ts
// User에서 id, createdAt만 빼고 나머지 + email/password 추가
export type SignUpInput = Omit<User, 'id' | 'createdAt'> & {
  email: string;
  password: string;
};

// Diary에서 id, content, charCount만 골라 쓰기
export type UpdateDiaryInput = Pick<Diary, 'id' | 'content' | 'charCount'>;
```

**주의**: `Omit<T, K>`는 `K`가 실제로 `T`에 존재하는 필드인지 검증하지 않는다. 오타(`'CreatedAt'`처럼 대소문자 틀림)를 내도 에러 없이 조용히 무시되고, 의도한 필드가 안 빠진 채로 넘어가버린다 — 눈에 띄는 에러 없이 잘못된 타입이 조용히 만들어지는 흔한 실수 포인트. `Pick<T, K>`는 반대로 `K`가 `keyof T`여야만 해서 오타 내면 바로 에러로 잡힌다.

### 어디서 쓰이나
- `User`, `Diary` 같은 "완전한 타입" → DB에서 **읽어온** 데이터를 다룰 때
- `SignUpInput`, `CreateDiaryInput`처럼 `id`/`createdAt` 등을 뺀 타입 → 아직 DB에 저장 전이라 값이 없는 필드들을 뺀, 함수에 **넘겨줄 때** 쓰는 파라미터 타입

## `export` — 파일 간 공유

파일 하나하나는 기본적으로 독립된 공간이라, `export` 없이 선언한 타입/함수는 그 파일 밖에서 `import`할 수 없다. 여러 파일(화면 코드, 다른 로직 파일)에서 같은 타입/함수를 공유하려면 반드시 `export`가 필요하다.

## UUID는 TS에서 그냥 `string`

Postgres 같은 DB엔 `uuid` 전용 타입이 있지만, TypeScript엔 그런 전용 타입이 없다. UUID 자체가 `"550e8400-e29b-..."` 형태의 문자열일 뿐이라, TS 코드에서는 `id: string`으로 받는다. DB 쪽만 특별 취급하는 것이고 JS로 넘어오면 그냥 일반 문자열.

## snake_case ↔ camelCase 변환이 필요한 이유

- SQL/DB 세계 관례: snake_case (`is_exchange_student`)
- JS/TS 세계 관례: camelCase (`isExchangeStudent`)

단순 취향 차이가 아니라 **Postgres의 기술적 제약**도 있다 — 따옴표 없이 쓴 컬럼명은 Postgres가 전부 소문자로 바꿔버린다. `isExchangeStudent`라고 컬럼을 만들면 실제론 `isexchangestudent`로 저장되어, 나중에 코드에서 `isExchangeStudent`로 조회하면 "그런 컬럼 없음" 에러가 난다. 그래서 DB 쪽은 밑줄(대소문자 이슈 없음)을 표준으로 쓰고, JS 쪽 코드가 이를 넘겨받는 지점(API 함수 안)에서 이름을 직접 매핑해준다.

```ts
.insert({
  is_exchange_student: profile.isExchangeStudent, // DB용 이름 ← JS용 이름
})
```

필드가 적을 때는 이렇게 함수마다 직접 매핑하는 편이 "뭐가 뭐로 바뀌는지" 눈에 보여서 낫다. 필드가 아주 많아지면 범용 변환 함수로 리팩토링을 고려할 수 있음.

## CRUD

데이터를 다루는 네 가지 기본 동작.

- **C**reate — 만들기
- **R**ead — 읽기
- **U**pdate — 수정하기
- **D**elete — 삭제하기

Zing에서는 `createDiary`(C), `getDiaries`(R), `updateDiary`(U), `deleteDiary`(D)로 대응.

## JavaScript는 무엇 위에 만들어졌나 (참고)

TypeScript는 JavaScript의 확장(superset)이지만, JavaScript 자체는 특정 한 언어의 확장이 아니라 여러 언어의 영향을 받아 독립적으로 만들어진 언어다 — 문법은 Java, 함수 처리 방식은 Scheme, 객체 모델(프로토타입 기반)은 Self의 영향을 받았다. ES6부터 `class` 문법이 생겼지만 내부적으로는 여전히 프로토타입 방식으로 동작하는 문법적 설탕(syntactic sugar)이라, JS는 "OOP 전용 언어"가 아니라 객체지향/함수형/절차형을 자유롭게 섞어 쓰는 멀티패러다임 언어다.
