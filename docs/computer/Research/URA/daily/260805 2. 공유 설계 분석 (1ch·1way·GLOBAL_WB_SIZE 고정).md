## 1. 우리가 겪은 문제와 이번 설계의 근본적 차이

|우리가 했던 방식|이번 공유 자료|
|---|---|---|
|write buffer|채널×LUN에 비례(축소 시 64KiB로 작아짐) → 크래시|`GLOBAL_WB_SIZE (MB(1))` 고정 → 항상 여유 있음|
|MDTS|6→4로 축소 시도(경계값이라 불안정)|6 그대로 유지, 문제없음|
|파일시스템|mkfs.ext4 + mount (journal 생성 중 대량 write로 크래시 발단)|**mount 안 함**, `fio --filename=/dev/nvme1n1`로 raw device에 직접 I/O|
|GC 확인 방법|dmesg의 `GC-ing` 로그를 grep으로 카운트|`conv_ftl.h`에 `gc_count` 필드를 직접 추가해 FTL 내부에서 정확히 카운트 (`SU Modded` 주석으로 표시)|
|실험 크기 설계|시행착오로 --size 값을 조정(1G→200M→3G)|아래 계산식으로 **필요한 정확한 크기를 사전 산출**|

## 2. 설정값

```c
NAND_CHANNELS = 1
LUNS_PER_NAND_CH = 1
PLNS_PER_LUN = 1
GLOBAL_WB_SIZE = MB(1)
BLKS_PER_PLN = 8192
```

NVMeVirt용 물리 메모리(memmap_size): **32GiB**

**1채널·1LUN·1플레인 구조에서는 "line"이 사실상 하나의 NAND block과 1:1 대응.** (병렬로 걸칠 채널/LUN이 없으므로 line = block)

## 3. 용량 계산 (보충 슬라이드 내용)

### 3-1. 전체 Line 수와 Line 크기

```
Blocks per Plane = 8192  → 총 8192 Line (32GiB를 8192등분)
Line(Block) Size = 32GiB / 8192 = 4MiB
```

### 3-2. Over-Provisioning 적용 후 실제 접근 가능 용량

```c
#define OP_AREA_PERCENT (0.07)   // 7% 오버프로비저닝
```

```
Host Accessible Capacity = 32GiB × (100/107) ≈ 29.91GiB
접근 가능 Line 수 = 8192 × (100/107) ≈ 7656.07 Line
```

→ 나머지 7%(약 536 Line)는 항상 SSD 내부적으로 예약되어 GC 등에 쓰이고, 호스트에게는 안 보이는 여유 공간.

### 3-3. Preconditioning 후 남는 Free Line

```
fio 100% 순차 쓰기로 preconditioning → 29.91GiB 전부 씀
→ 이 시점에 남는 Free Line = 535개
```

(8192 총 Line 중, 접근 가능한 7656 Line을 다 채웠지만 OP 영역 등으로 인해 535 Line은 여전히 free 상태로 남음)

### 3-4. GC를 확실히 트리거하는 데 필요한 추가 write량

```c
cpp->gc_thres_lines_high = 2;   // free line이 2 이하로 떨어져야 GC 발동
```

```
535개의 free line 중, 최소 533개(535-2)를 추가로 소비해야 GC 임계값(free=2)에 도달
533 Line × 4MiB(Line 크기) = 2132MiB
```

→ 여유를 두어 **preconditioning 이후 2200MiB(2200M)를 추가로 순차 덮어쓰기**하면 확실히 GC 임계값(free≤2)에 도달함.

**이게 `seq_gc_invoke.sh`의 `--size=2200M`이 그 숫자로 정해진 이유.** (README의 "왜 2200MB로 했는지" 질문에 대한 답)

## 4. Write Credit 메커니즘 (16MiB 실험, `fio_write_16M.sh`)

```
fio 요청 크기 = 256KiB
1 요청 = 256KiB / 4KiB(FTL page) = 64 write credit 소모
Line 하나의 write credit = 1024개
1024 / 64 = 16 요청마다 Line 하나 소진
16 요청 × 256KiB = 4MiB = Line 크기와 일치 (검증됨)

16MiB 순차 쓰기 = 총 64 요청 = Line 4개 분량
```

→ 이 실험은 GC 없이, 순수하게 "write credit이 줄어들다가 0이 되면 다음 free line으로 이동 후 재충전되는" 기본 메커니즘만 관찰하는 목적 (line ≠ GC 대상, 아직 free line이 충분한 상태)

---

## 5. 실험 절차 요약

### 실험 1 — 16MiB 순차 쓰기 (write credit 메커니즘 관찰)

```bash
./fio_write_16M.sh
```

확인 포인트: 요청마다 credit 감소 → credit 0 → 다음 free line 이동 → credit 재충전

### 실험 2 — Preconditioning + GC 유발

```bash
./preconditioning.sh      # 전체(100%, 29.91GiB) 순차 쓰기로 채움 (~4분)
                            # (재초기화 없이 바로 이어서)
./seq_gc_invoke.sh         # 2200MiB 추가 순차 덮어쓰기 (~15초) → GC 트리거
```

확인 포인트:

- GC 발생 시 write latency 증가 여부
- latency spike 개수와 `gc_count`(FTL 내부 카운터) 대응 여부
- Line 크기(4MiB)/요청 크기(256KiB) 비율상 **약 16개 요청마다 latency spike**가 나타나는지

## 6. 주의사항 (README 원문 요약)

1. **절대 mount하지 않음** — raw block device에 직접 I/O (파일시스템의 Used%는 진행 상태 지표가 아님)
2. 실행 전 `lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL`로 디바이스 재확인 (잘못 지정 시 데이터 삭제 위험)
3. 실험 1과 실험 2는 서로 독립 — 사이에 NVMeVirt 재초기화 필요
4. **Preconditioning과 GC 유발 workload 사이에는 절대 재초기화하지 않음** (모듈 재로드/재부팅/format 시 preconditioning 상태 소실)
5. 실험 중 다른 I/O 발생 금지 (동시 접근 시 측정값 왜곡)
6. fio 3.36에서 `--log_issue_time=1` 옵션 미지원 — 사용하지 않음
7. 종료 전 fio 결과 파일, latency 로그, 커널 로그, line/write credit 상태를 모두 보존

## 7. 앞으로 실험에 적용할 것

- `GLOBAL_WB_SIZE (MB(1))`로 고정하고 1채널×1LUN으로 재구성 (크래시 없이 진행 가능할 것으로 예상)
- mount 없이 raw device(`--filename=/dev/nvme1n1`)로 직접 fio 실행 — mkfs 관련 크래시 위험 원천 차단
- `conv_ftl.c`에서 `SU Modded` 검색해 `gc_count` 계측 코드 확인, 우리 실험에도 반영해 dmesg grep보다 정확한 카운트 확보
- preconditioning(전체 채우기) → GC 유발(재기록) 두 단계로 스크립트 분리
