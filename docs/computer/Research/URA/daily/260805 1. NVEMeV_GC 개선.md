# Write Buffer / MDTS / 채널·LUN 관계 정리

> 1채널×1LUN 설정에서 발생했던 크래시의 원인과, 이후 제안된 해결책이 왜 통하는지 정리.

---

## 1. Write Buffer 크기와 채널/LUN의 관계

`ssd_config.h`:

```C
#define GLOBAL_WB_SIZE (NAND_CHANNELS * LUNS_PER_NAND_CH * ONESHOT_PAGE_SIZE * 2)
```

**의미**: SSD가 호스트로부터 write 요청을 받으면, 곧바로 NAND에 쓰는 게 아니라 먼저 이 write buffer(임시 저장 공간)에 담아둠. 이 버퍼의 크기는 **채널 수 × LUN 수 × 한 번에 쓰는 페이지 크기 × 2**로 계산됨 — 채널/LUN이 많을수록(=병렬 처리 유닛이 많을수록) 그만큼 동시에 처리할 데이터를 담을 공간도 커야 하므로, 버퍼 크기가 채널·LUN 수에 비례하도록 설계되어 있음.

**우리가 겪은 문제**

```
NAND_CHANNELS = 1, LUNS_PER_NAND_CH = 1  (GC를 빨리 유발하려고 디스크를 작게 만들 목적으로 축소)
→ GLOBAL_WB_SIZE = 1 × 1 × 32KB × 2 = 64KiB
```

채널/LUN을 극단적으로 줄이자, 원래 8×2 기준이면 컸을 버퍼가 **64KiB로 지나치게 작아짐.**

---

## 2. MDTS를 줄이려고 했던 이유

**MDTS(Maximum Data Transfer Size)**: 호스트가 SSD에 한 번에 보낼 수 있는 최대 요청 크기. NVMe 표준상 `2^MDTS × (기준 페이지 크기, 4KB)`로 계산됨.

```
MDTS = 6  →  2^6 × 4KB = 256KiB
```

**문제의 핵심 — 버퍼(64KiB)보다 요청 크기(최대 256KiB)가 더 클 수 있었음**

호스트가 이론상 최대 256KiB짜리 요청을 보낼 수 있는데, 그걸 받아줄 write buffer는 64KiB밖에 안 됨. 즉:

```
버퍼 용량(64KiB) < 요청 최대 크기(256KiB)
```

이 상태에서 큰 요청이 들어오면 버퍼가 감당하지 못해 `buffer_allocate` 함수에서 실패 → I/O timeout → 디바이스 응답 불능 → 커널 크래시로 이어짐.

**그래서 MDTS를 낮추는 게 합리적인 해결책처럼 보였던 이유**

```
MDTS를 4로 낮추면 → 2^4 × 4KB = 64KiB → 요청 최대 크기(64KiB) = 버퍼 크기(64KiB)
```

요청 크기의 상한을 버퍼 크기와 맞춰서, "버퍼보다 큰 요청이 들어오는" 상황 자체를 차단하려는 접근이었음.

---

## 3. MDTS를 낮췄는데도 왜 완전히 해결되지 않았는가

**딱 맞아떨어지는 경계값이라는 것 자체가 문제였음**

```
MDTS=4 → 요청 최대 64KiB
버퍼 크기 → 64KiB
```

숫자상으로는 "요청 ≤ 버퍼"라 안전해 보이지만, 실제로는:

- 버퍼가 요청 크기와 **정확히 같으면**, 메타데이터나 정렬(alignment) 등을 위한 여유 공간이 없어 경계 조건에서 여전히 실패할 수 있음
- 여러 요청이 동시에(파이프라인으로) 처리될 경우, 한 순간에 버퍼가 여러 요청을 동시에 감당해야 하는데 64KiB 버퍼 하나로는 여유가 없음

MDTS를 4로 낮춘 뒤에도 mkfs.ext4의 journal 생성 단계에서 동일한 timeout이 재현됨을 확인함. 즉 MDTS 축소는 "이론상 딱 맞춘" 미봉책이었고, 실제 버퍼 운용 여유(margin) 부족 문제는 해결하지 못함.

**실제로 이 문제인지는 모르겠음** MDTS를 3으로 낮춘후에 돌려본적이 없음.

## 4. 이번 해결책이 통하는 이유 — GLOBAL_WB_SIZE 고정

```c
#define GLOBAL_WB_SIZE (MB(1))   // 채널·LUN 값과 무관하게 무조건 1MB로 고정
```

**핵심 변화**: 기존에는 `GLOBAL_WB_SIZE`가 `NAND_CHANNELS × LUNS_PER_NAND_CH`에 **종속된 계산값**이었지만, 이제 채널/LUN을 얼마로 설정하든 **버퍼 크기를 1MB로 고정**시켜버림.

```
채널/LUN을 1×1로 줄여도 → GLOBAL_WB_SIZE = 1MB (변하지 않음)
MDTS 6 기준 요청 최대 크기 = 256KiB

→ 버퍼(1MB) ≫ 요청 최대 크기(256KiB)
```

버퍼가 요청 크기보다 **4배 이상 여유 있게** 크기 때문에, 경계에 걸리는 상황 자체가 발생하지 않음. 이게 근본적인 해결이 되는 이유: **버퍼 크기를 채널/LUN 설정과 분리시켜, "채널/LUN을 어떻게 줄이든 버퍼는 항상 충분히 크게 유지"**하는 구조로 바꾼 것.

---

## 5. 왜 MDTS를 줄이지 않아도 되는가

기존에는 `GLOBAL_WB_SIZE`가 채널/LUN 축소에 따라 같이 작아졌기 때문에, 버퍼 부족을 피하려면 **요청 크기(MDTS) 쪽을 줄이는 수밖에 없었음.** 즉 "작아진 그릇에 맞춰 담을 양을 줄이는" 접근.

이번 해결책은 반대로 **"그릇(버퍼) 자체를 항상 충분히 크게 고정"**해버렸기 때문에, 담을 양(MDTS가 허용하는 요청 크기)을 줄일 필요가 없어짐:

```
버퍼가 1MB로 고정되어 있으면
MDTS=6(요청 최대 256KiB)이든, 원래 그대로 두든
어차피 버퍼가 4배 이상 여유 있으므로 문제없음
```

**정리 — 두 접근의 근본적 차이**

|접근|방식|결과|
|---|---|---|
|MDTS 축소 (기존 시도)|요청 크기를 버퍼에 맞춰 줄임|경계값이라 여전히 불안정|
|GLOBAL_WB_SIZE 고정 (새 해결책)|버퍼를 요청 크기보다 항상 크게 고정|근본적으로 안전, MDTS 원래값 유지 가능|

---

## 6. 부가 — "line을 block으로 인식해도 무방"

채널/LUN이 8×2처럼 여러 개일 때는 "line"이 여러 채널·LUN에 걸쳐 병렬로 기록되는 스트라이프(여러 블록의 묶음) 단위였음. 채널/LUN이 1×1이 되면 병렬로 걸칠 대상 자체가 없어지므로, line 하나가 곧 block 하나와 동일해짐 (line = block 1:1 대응).

---

## 7. 다음 실험에 적용할 수 있는 것

- `GLOBAL_WB_SIZE (MB(1))`로 고정하고 `NAND_CHANNELS=1, LUNS_PER_NAND_CH=1`로 다시 축소 → 크래시 없이 디스크 자체를 작게 만들어 GC를 더 빠르고 확실하게 유발 가능
- 기존 `memmap_size` 축소 방식과 병행하거나 대체하는 방향으로 재실험 고려
