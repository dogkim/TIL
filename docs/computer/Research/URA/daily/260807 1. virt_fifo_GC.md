## 진행 순서

### 1. 검증 코드 작성 
(순차 쓰기에서 기존 Greedy가 결과적으로 FIFO처럼 동작하는지 확인)
- 각 line이 "몇 번째로 마감(full)됐는지" 기록하는 `write_seq` 필드 추가
- GC가 victim으로 고른 line의 `write_seq`를 로그에 남겨, 순서대로(오름차순) 선택되는지 확인
- 목적: 순차 쓰기 조건에서는 "먼저 채워진 line"과 "invalid가 가장 먼저 쌓이는 line"이 항상 일치하므로, Greedy(vpc 기준)와 FIFO가 같은 line을 고를 것이라는 가정 확인

### 2. FIFO 구현 후 1번과 비교
- 같은 조건(순차 쓰기)에서 Greedy 결과와 동일하게 나오는지 비교
- 같으면 가설 검증 완료로 패스, 다르면 원인 분석

### 3. Random Write로 전환 후 FIFO vs Greedy 비교
- 순차 쓰기에서는 두 정책이 구분되지 않으므로, 같은 LBA 재사용 패턴이 불규칙한 랜덤 쓰기로 전환해 실제 차이가 드러나는지 확인

### 3. Victim 우선순위 함수
```C
static inline pqueue_pri_t victim_line_get_pri(void *a)
{
#if GC_POLICY_FIFO
    return ((struct line *)a)->write_seq;
#else
    return ((struct line *)a)->vpc;
#endif
}

static inline void victim_line_set_pri(void *a, pqueue_pri_t pri)
{
#if GC_POLICY_FIFO
    ((struct line *)a)->write_seq = pri;
#else
    ((struct line *)a)->vpc = pri;
#endif
}
```

### 4. `static void mark_page_invalid()`
우선순위 값을 새로 지정하고(set_pri 호출) + 큐 안에서 재정렬

- greedy: 기존 `pqueue_change_priority` 유지 (vpc 감소 시 pqueue 재정렬 필요)
- FIFO: 재정렬 호출 시 write_seq가 vpc-1로 오염되는 상황 발견 
	-> `line->vpc--`만 직접 수행하도록 수정

```C
    if (line->pos) {
        /* Note that line->vpc will be updated by this call */
        //DG Modded start : FiFO
        #if GC_POLICY_FIFO
            line->vpc--;
        #else
            pqueue_change_priority(lm->victim_line_pq, line->vpc - 1, line);
        #endif
        //DG Modded end
    } else {
        line->vpc--;
    }
```

### 5. `static void advance_write_pointer()`
 line 마감 시 write_seq 부여

```C
if (wpp->curline->vpc == spp->pgs_per_line) {
        /* all pgs are still valid, move to full line list */
        NVMEV_ASSERT(wpp->curline->ipc == 0);
        wpp->curline->write_seq = conv_ftl->line_seq_counter++;   // DG Modded
        list_add_tail(&wpp->curline->entry, &lm->full_line_list);
        lm->full_line_cnt++;
        NVMEV_DEBUG_VERBOSE("wpp: move line to full_line_list\n");
    } else {
        NVMEV_DEBUG_VERBOSE("wpp: line is moved to victim list\n");
        NVMEV_ASSERT(wpp->curline->vpc >= 0 && wpp->curline->vpc < spp->pgs_per_line);
        /* there must be some invalid pages in this line */
        NVMEV_ASSERT(wpp->curline->ipc > 0);
        wpp->curline->write_seq = conv_ftl->line_seq_counter++;   // DG Modded
        pqueue_insert(lm->victim_line_pq, wpp->curline);
        lm->victim_line_cnt++;
    }
```

## 실험 결과

**(a) Seq, Greedy — write_seq 및 rmmod 최종 통계**:

`write_seq` 값이 처음부터 끝까지 역전 없이 오름차순으로만 나옴:
```
0, 1, 3, 7, 15, 31, 63, 127, 255, 511, 532, 533, 534, ..., 739
```

| 항목 | 값 |
|---|---|
| tt_lines | 8192 |
| full_line_cnt | 7655 |
| free_line_cnt | 3 |
| write_credits | 192 |
| victim_line_cnt | 532 |
| gc_count | 218 |

- **결론**: 순차 쓰기 조건에서, vpc 기준 victim 선택이 "가장 먼저 채워진 line부터" 도출됨

**(b) Seq, FIFO — write_seq 및 rmmod 최종 통계**:

`mark_page_invalid()` 수정(`line->vpc--`만 수행) 후 재실행:
```
0, 1, 2, 3, ..., 217
```

`pqueue_change_priority` 호출이 기존 greedy의 erase 순서를 바꾼것으로 보임

| 항목 | 값 |
|---|---|
| tt_lines | 8192 |
| full_line_cnt | 7655 |
| free_line_cnt | 3 |
| write_credits | 192 |
| victim_line_cnt | 532 |
| gc_count | 218 |

**Greedy(vpc) vs FIFO, 순차 쓰기 비교**:

| 항목                     | Greedy(vpc)           | FIFO                  |
| ---------------------- | --------------------- | --------------------- |
| gc_count               | 218                   | 218                   |
| write_seq 순서           | 완전 오름차순               | 완전 오름차순               |
| clat p99 / p99.9 / max | 5211 / 5342 / 5320 us | 5211 / 5211 / 5286 us |
| 이상값                    | 없음                    | 없음                    |

완전히 동일한 GC 발생 횟수(218)와 동일한 선택 순서 패턴, 거의 동일한 latency 분포를 통해 **순차 쓰기 조건에서는 Greedy(vpc)와 FIFO 정책이 사실상 동일하게 동작한다**는 가설이 확인

**Latency 그래프 (Seq, Greedy / Seq, FIFO)**: 
precondition 구간(0~15초, ~1700us대 평탄)과 seq_gc_invoke 진입 후(15초 이후) GC로 인한 latency가 약 5500~5600us 수준으로 계단식 상승하는 패턴이 유사하게 등장

### 4) Random Write 비교 — Greedy vs FIFO

`--rw=write` → `--rw=randwrite`로 전환한 `rand_gc_invoke.sh`(3000M) 실행.
나머지는 위와 동일

**(a) Random, Greedy — write_seq 및 rmmod 최종 통계**

```
558, 191, 64, 484, 65, 305, 308, 102, 218, 694, ...(불규칙)
```

| 항목              | 값    |
| --------------- | ---- |
| tt_lines        | 8192 |
| full_line_cnt   | 7655 |
| free_line_cnt   | 3    |
| write_credits   | 192  |
| victim_line_cnt | 532  |
| gc_count        | 218  |
Seq, Greedy와 **gc_count·free_line_cnt·victim_line_cnt 등 모든 최종 수치가 완전히 동일**함. 다만 `write_seq` 선택 순서는 순차 때와 달리 뒤섞여서 나타남:

**해석**: Greedy는 오직 그 순간의 `vpc`(valid page 개수)만 보고 victim을 고르므로, write 패턴이 순차든 랜덤이든 가장 싼 line을 고르는 결과 자체(GC 총량, 최종 free space)는 동일하게 나타남

**(b) Random, FIFO — write_seq 및 rmmod 최종 통계:**

`write_seq`는 랜덤 쓰기 조건에서도 흐트러짐 없이 완전한 오름차순으로 나타남:
```
0, 1, 2, 3, ..., 254
```

| 항목              | 값    |
| --------------- | ---- |
| tt_lines        | 8192 |
| full_line_cnt   | 7655 |
| free_line_cnt   | 2    |
| write_credits   | 448  |
| victim_line_cnt | 533  |
| gc_count        | 255  |
**해석**: FIFO는 write 패턴과 무관하게 "가장 먼저 채워진 line"을 기계적으로 고르기 때문에, 랜덤 쓰기에서도 victim 선택 순서 자체는 항상 write_seq 순으로 유지됨
다만 아직 valid 데이터가 많이 남아있는 line을 선택, 매 GC마다 옮겨야 할 데이터가 Greedy보다 커짐 
- 그 결과 동일한 write량에서 GC가 **218회(Greedy) → 255회(FIFO)로 더 자주** 발생

**Greedy vs FIFO, 랜덤 쓰기 비교**:

| 항목 | Random, Greedy | Random, FIFO |
|---|---|---|
| gc_count | 218 | **255** |
| free_line_cnt(최종) | 3 | 2 |
| victim_line_cnt | 532 | 533 |
| write_seq 순서 | 불규칙(무작위) | 완전 오름차순 |
| clat p99 / p99.9 / max | 5211 / 5276 / 5323 us | **10028 / 22152 / 31693 us** |

**Latency 그래프**: Random·Greedy는 Seq 결과들과 거의 동일한 형태(15초 이후 ~5500us 평탄 상승)를 보이는 반면, Random·FIFO는 15초 이후 latency가 8000~30000us 범위에서 넓게 산개하며 스파이크 폭이 훨씬 크고 불규칙함

## 결론

- **순차 쓰기**
	1. Greedy(vpc)와 FIFO(write_seq)가 사실상 동일한 line을 선택, 큰 차이가 드러나지 않음

- **랜덤 쓰기**
  1. Greedy는 어떤 워크로드든 "정리 비용이 가장 싼 line"을 우선하므로 GC 총량이 워크로드 패턴과 무관하게 안정적(218회로 동일)
  2. FIFO는 정리 비용을 고려하지 않고 오래된 순서만 따르므로, 랜덤 쓰기에서 valid 데이터가 많이 남은 line을 GC하게 되는 경우가 늘어 **GC 횟수(255회)와 tail latency(최대 31.7ms, Greedy 대비 약 6배) 모두 크게 증가**
  
- 즉 FIFO는 선택 순서가 항상 write_seq 순이므로, "정리 비용을 고려하지 않는다"는 점에서 랜덤 워크로드에서 성능 저하로 직접 드러남을 확인
