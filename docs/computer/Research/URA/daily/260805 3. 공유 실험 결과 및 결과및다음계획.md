# NVMeV GC 실험 — Raw Device 방식 (장성욱님 설계 적용)

>  공유받은 GLOBAL_WB_SIZE 고정 + raw device 방식을 적용한 실험 기록. 10시 사용 시간 종료로 본 실험(18회 GC 확인)까지만 진행

---

## 1. 오늘 실험 요약

### 적용한 설정 (공유 자료 기반)
```c
NAND_CHANNELS = 1
LUNS_PER_NAND_CH = 1
PLNS_PER_LUN = 1
GLOBAL_WB_SIZE = MB(1)      // 채널/LUN 값과 무관하게 고정 → 이전 크래시(buffer_allocate) 원인 해소
MDTS = 6                     // 낮출 필요 없음 (버퍼가 충분히 커서)
NAND_ERASE_LATENCY = 3500000
```
`insmod memmap_size=32G` — 32GiB 가상 SSD.

**mount 하지 않음** — `fio --filename=/dev/nvme1n1`로 raw device에 직접 I/O (mkfs 관련 크래시 위험 자체를 제거).

### conv_ftl.c 수정
`do_gc()` 안에 있던 코드
```c
conv_ftl->gc_count++;   // 수정: GC 발생마다 누적
```
으로 고침. 이 상태로 재빌드 후 진행.

### 실험 절차
```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL   # nvme1n1 = CSL_Virt_MN_01, 29.9G, FSTYPE/MOUNTPOINTS 비어있음(raw) 확인
./preconditioning.sh    # --size=100%, 전체(29.9GiB) 순차 쓰기
./seq_gc_invoke.sh       # --size=2200M, 추가 순차 쓰기로 GC 유발
sudo rmmod nvmev          # 종료 시 remove_lines()가 최종 통계 자동 출력
```

### 최종 결과 (rmmod 시점 dmesg)
```
tt_lines: 8192
full_line_cnt: 7655
free_line_cnt: 3
write_credits: 192
victim_line_cnt: 532
gc_count: 18
```

**검증된 것**
- `tt_lines`(8192), `full_line_cnt`(7655)가 사전 계산값(8192, ≈7656)과 거의 정확히 일치
- `free_line_cnt`가 임계값(2) 바로 근처(3)에서 실험 종료 — GC가 정상적으로 임계 조건까지 작동했음을 확인
- `gc_count: 18` — 이번 seq_gc_invoke(2200M) 실행에서 실제 GC 발생 횟수를 코드 레벨에서 정확히 계측 성공 (dmesg grep으로 세던 이전 방식보다 신뢰도 높음)

## 3. Threshold를 높이면 GC 간격이 어떻게 될지 — 예측과 정정

### 초기 예측
"threshold(`gc_thres_lines_high`)를 높이면, GC가 더 자주 발생해서 그래프에서 스파이크 간격이 촘촘해져 패턴을 알아보기 어려워질 것"이라고 처음 추정함.

### 검증 — write credit 체크 주기는 threshold와 무관
```c
static inline void check_and_refill_write_credit(struct conv_ftl *conv_ftl)
{
    if (wfc->write_credits <= 0) {   // 이 체크는 16번째 요청마다 항상 발생 (bs=256k 기준 고정)
        foreground_gc(conv_ftl);      
        // 이 안에서 실제 GC 실행 여부만 threshold에 좌우됨
        ...
    }
}
```
`요청 크기(256KiB)`와 `Line의 총 credit(1024)`으로 정해지는 **"16개 요청마다 체크한다"는 주기 자체는 threshold 값과 무관하게 항상 고정**임을 코드로 확인.

### 정정된 결론
-  **GC와 GC 사이의 간격(16개 요청)** 자체는 threshold와 무관하게 그대로 유지됨. 다만 threshold를 높이면 그 일정한 간격의 스파이크가 이른 시점에 발생

### 대안 방안 (다음 실험에 적용)
1. **그래프를 구간 확대(zoom-in)해서 확인**: 전체 구간을 다 보지 않고, 일부 구간(예: 요청 100~200번째)만 잘라서 16개 간격 패턴이 실제로 보이는지 시각적으로 검증
2. **`--bs`(요청 크기) 조정으로 체크 주기 자체를 늘리는 것도 병행 고려**: `bs`를 줄이면(예: 256k→64k) 체크 주기가 16 → 64개로 늘어나 그래프상 스파이크 간격이 넓어짐 — threshold 실험과 별개로, 주기 자체를 조정하고 싶을 때 쓸 수 있는 방법으로 확인해둠 (재빌드 불필요, fio 옵션만 조정)
