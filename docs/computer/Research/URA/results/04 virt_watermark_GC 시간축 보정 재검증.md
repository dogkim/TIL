# Watermark GC 실험 — 시간축 보정 재검증

[[03 virt_watermark_GC (High-Low Watermark) 실험 결과|03번 보고서]]에서 남겨뒀던 문제, "`/proc/uptime`을 수동으로 찍어 계산한 시작 시각과 실제 dmesg GC 발생 시점 사이에 오차가 있었다"는 이슈를 해결하고 재측정한 결과.

## 시간 측정 방식 수정

**기존 방식(오차 있음)**: 사람이 커맨드 실행 직전/직후에 `/proc/uptime`을 수동으로 찍어 `START_TIME` 계산 — 커맨드 입력 지연, 이전 실행 잔여 등으로 오차 발생.

**수정 방식**: fio 실행 시 `--output-format=json`으로 받은 결과의 `job_start`(에폭 타임스탬프, ms 단위)를 시작 시각으로 사용. dmesg의 커널 타임스탬프(부팅 이후 초 단위)와는 별도 기준이므로, `uptime -s`(부팅 시각)와 조합해 둘을 같은 좌표계로 환산한 뒤 GC 로그의 발생 시점을 "`seq_gc_invoke` 시작 이후 경과 시간(s)"으로 정확히 계산.

이 보정 덕분에, 이전 보고서에서 그래프 x축이 실제 GC 발생 구간과 어긋나 보이던 문제가 해결되고, **버스트가 정확히 몇 초 지점에서 얼마나 짧게 일어나는지**까지 측정 가능해짐.

### low=134, high=2

`seq_gc_invoke` 시작 후 **약 11.98초 지점**과 **약 16.26초 지점**, 정확히 **두 번**의 burst가 관찰됨 — 03번 보고서에서 "큰 latency 스파이크가 두 번 관찰됨"이라고 추정했던 것을 정확한 시각으로 확인.

`gc_log_2682.txt` 기준, **약 11.96초 지점**에서 단 **한 번**의 burst만 관찰됨 — `free_line_cnt`가 2에서 268까지 수직으로 튀어오름. 소요 시간은 첫~마지막 GC 타임스탬프 차이(`93022.951305` → `93022.953352`) 기준 **약 2.05ms**로, low=134 burst보다 처리하는 line 수(267개)가 약 2배 많은 만큼 소요 시간도 거의 비례해서 늘어남.

## 결론

- 시간축 보정 후에도 03번 보고서의 정성적 결론(low가 낮을수록 자주·작게, 높을수록 드물게·크게 몰아침)은 그대로 재확인됨 — 이번 보정으로 얻은 것은 **정확한 발생 시각과 burst 소요 시간**이라는 정량적 디테일.
- **burst 소요 시간이 매우 짧음(ms 단위)**: while 루프가 중간에 다른 작업 없이 GC만 연속으로 처리하기 때문 — 처리해야 할 line 수(132개 vs 267개)에 거의 비례해서 burst 폭이 늘어남 (line당 처리 시간이 거의 일정, 약 8μs/line 수준으로 두 케이스에서 일관됨: 1.06ms/132 ≈ 8.0μs, 2.05ms/267 ≈ 7.7μs).
- low=134에서 burst가 **정확히 두 번, 거의 동일한 간격·모양으로 재현**된다는 것은, opportunistic GC 없이 순수하게 워크로드의 쓰기 속도만으로 free_line이 소진되는 주기가 일정하다는 것을 시사함 — 다음 실험에서는 이 burst 간격(약 4.3초)이 `--bs`나 `--size`를 바꿨을 때 어떻게 변하는지 확인해볼 수 있음.
