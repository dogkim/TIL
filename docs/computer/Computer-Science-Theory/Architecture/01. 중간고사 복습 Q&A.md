## 1. ISA 비교 (Intel / ARM / AMD)

Intel과 AMD는 같은 **CISC(x86) ISA**를 쓰지만, 그걸 실제로 구현하는 **마이크로아키텍처는 서로 다름**. ARM은 애초에 **RISC ISA**를 사용.

## 2. CPU 개수를 늘리면 성능이 선형적으로 증가하는가?

**선형적으로 증가하지 않음** — **암달의 법칙(Amdahl's Law)** 때문. 프로그램 내 병렬화 불가능한 순차 부분이 있으면, 코어를 아무리 늘려도 그 부분이 전체 실행시간의 하한을 결정함.

## 3. Benchmark란?

시스템에서 발생하는 **특정한 유형의 작업부하(workload)를 흉내내도록 설계**된 표준화된 프로그램/테스트 — 서로 다른 시스템의 성능을 일관된 기준으로 비교하기 위해 사용.

## 4. RV64에서 "64"의 의미

**메모리 주소의 크기**와 **레지스터의 개별 용량(폭)**이 64비트라는 뜻.

## 5. Power Wall 해결을 위해 도입된 아키텍처

**Multi-core architecture** — 단일 코어의 클럭을 계속 올리는 대신, 여러 개의 코어를 두어 전력 소모를 억제하면서 성능을 확보.

## 6. Frequency, 개별 CPI, 평균 CPI

$$\text{CPU Time} = \text{Instruction Count} \times \text{CPI} \times \text{Clock Cycle Time} = \frac{\text{Instruction Count} \times \text{CPI}}{\text{Frequency}}$$

**평균 CPI**는 명령어 종류별 CPI를 그 명령어가 실행에서 차지하는 **비중(빈도)으로 가중평균**한 값:
$$\text{Average CPI} = \sum_i (\text{CPI}_i \times \text{비율}_i)$$

## 7. 산술/기하/조화 평균, 언제 어떤 것을 쓰는가

- **산술평균(Arithmetic mean)**: 여러 프로그램의 **실행 시간**을 평균낼 때 (시간은 그대로 더해도 의미가 있는 값이므로)
- **기하평균(Geometric mean)**: **정규화된 비율(normalized ratio)**을 평균낼 때 — 어떤 기준 머신 대비 비율로 정규화된 값들은 기준을 바꿔도 기하평균의 상대적 비교 결과가 일관되게 유지됨
- **조화평균(Harmonic mean)**: **rate(비율값, 예: MIPS, FLOPS)**를 평균낼 때 — 분모가 되는 양(예: 시간)을 동일한 가중치로 다루고 싶을 때 사용

## 8. 레지스터 값을 0으로 만드는 방법

**XOR** 사용: `XOR R, R` → 같은 값끼리 XOR하면 항상 0. 즉시값을 로드하는 것보다 빠르고 命令 인코딩이 짧아 흔히 쓰이는 관용구.

## 9. 32bit 아키텍처에서 표현 가능한 가장 작은 음수

**$-2^{31}$** (2의 보수 표현에서 최상위 비트가 1이고 나머지가 전부 0인 경우)

## 10. 리틀 엔디안 vs 빅 엔디안

- **리틀 엔디안(Little-endian)**: 작은 자릿값(LSB)을 **작은 주소**에 저장
- **빅 엔디안(Big-endian)**: 큰 자릿값(MSB)을 **작은 주소**에 저장

## 11. Offset을 쓰면 왜 좋은가

베이스 레지스터 + offset(변위) 방식으로 주소를 지정하면:
- 매 명령마다 전체 절대주소를 담을 필요 없이, 베이스 레지스터 하나로 **주변의 여러 메모리 위치**(배열 원소, 구조체 필드, 스택 프레임의 지역변수 등)에 접근 가능
- 명령어에 담아야 할 즉시값(주소)의 비트 수가 줄어 **명령어 인코딩이 짧아짐**
- 베이스 주소만 바꾸면 같은 코드로 다른 데이터를 가리킬 수 있어 **위치 독립적 코드(PIC)**나 재배치에도 유리

## 12. Data Transfer Operation의 예시

레지스터 ↔ 메모리 간 데이터 이동 연산: **LOAD**(메모리 → 레지스터), **STORE**(레지스터 → 메모리), 레지스터 간 **MOVE** 등.

## 13. 암달의 법칙 — LOAD 사이클 5 → 2로 개선 시 %Time 계산

**풀이 방법(공식)**:
$$\text{Speedup} = \frac{1}{(1 - F) + \dfrac{F}{S}}$$

- $F$: 개선 대상(LOAD)이 전체 실행시간에서 차지하던 비율
- $S$: 개선 배율 = (기존 사이클 수) / (개선 후 사이클 수) = $5/2 = 2.5$

전체 실행시간 중 LOAD가 차지하던 비율 $F$를 알아야 실제 %Time 감소분을 계산할 수 있음 (원본 문제의 명령어 구성비 데이터가 남아있지 않아 숫자로 확정하지는 못했고, 위 공식에 $F$, $S=2.5$를 대입하면 됨).

## 14. 암달의 법칙 — 코어 개수 $p$일 때

$$\text{Speedup}(p) = \frac{1}{(1-F) + \dfrac{F}{p}}$$

$F$: 병렬화 가능한 부분의 비율, $(1-F)$: 순차적으로만 실행되어야 하는 부분의 비율. $p \to \infty$여도 $(1-F)$ 항은 줄어들지 않으므로 speedup은 $\frac{1}{1-F}$로 수렴(한계가 생김).

## 15. Memory-to-Register 연산을 Register-to-Register로 바꾸기

CISC 스타일의 "메모리 피연산자를 직접 쓰는 연산"(예: `ADD R1, Mem`)을, RISC(load/store) 스타일로 바꾸려면:
1. 먼저 **LOAD**로 메모리 값을 레지스터에 가져옴: `LOAD R2, Mem`
2. 그 다음 **레지스터끼리만** 연산: `ADD R1, R1, R2`

즉 "메모리 접근"과 "연산"을 분리해서, ALU 연산은 항상 레지스터만 다루도록 만드는 것 — load/store 아키텍처(RISC)의 핵심 설계 원칙.

## 16. Latency vs Rate vs Ratio (성능 지표 비교)

| 지표 | 장점 | 단점 |
|---|---|---|
| **Latency** | 개별 작업 하나가 얼마나 빨리 끝나는지 알 수 있음 (사용자 체감 관점) | 시스템 전체의 처리 효율성은 알 수 없음 |
| **Rate** | 전체 시스템의 처리량(throughput) 효율을 보여줌 | 개별 요청의 응답 속도(체감 지연)는 무시됨 |
| **Ratio** | 두 프로세서/시스템을 상대적으로 객관적 비교 가능 | 비율만 봐서는 절대적인 수치(실제로 얼마나 빠른지)를 알 수 없음 |

## 부록. User CPU Time vs System CPU Time

- **User CPU time**: 프로그램 자신의 코드를 실행하는 데 걸린 시간
- **System CPU time**: 그 프로그램을 대신해 OS가 I/O 처리, 시스템 콜 등을 수행하는 데 걸린 시간
