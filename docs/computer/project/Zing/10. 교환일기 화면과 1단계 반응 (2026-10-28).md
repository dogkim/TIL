### 1. 교환일기 화면

매칭 탭에서 상대를 누르면 "OO님과의 교환일기"로 이동한다.

- 나와 상대의 일기를 **한 목록에 최신순으로** 섞어서 보여줌. 교환일기 앱이니까 "주고받은 일기장"처럼 보이게 하려는 것. 내 일기는 회색 배경으로 구분.
- 위에 현재 단계와 **다음 단계까지 진행도**: `다음 단계까지 (매칭 후 일기) 나 0/2 · 상대 0/2`. 단계 기준이 "매칭 후 **둘 다** 쓴 일기 수"라서, 둘의 개수를 같이 보여주면 상대가 안 쓰고 있다는 것도 자연스럽게 보인다.
- 진행도는 화면에서 계산한 **표시용**이고, 실제 단계 판정은 DB `match_stage`가 한다. 기준값(2/4/7)은 `lib/constants.ts`의 `STAGE_THRESHOLDS`에 두고 DB와 맞춰야 한다고 주석을 달아둠.

### 2. 1단계 반응

- 상대 일기 아래에 이모지 5개(❤️ 😂 😮 😢 👏). 하나 누르면 선택, 다른 걸 누르면 교체, **같은 걸 다시 누르면 취소**.
- 일기 하나에 한 사람당 반응 1개 → PK를 `(diary_id, user_id)`로 잡아서 DB가 보장. 교체는 `on conflict do update`.
- 내 일기 아래에는 "OO님의 반응 👏" 또는 "아직 반응이 없어요".

### 3. 이번엔 정책을 아예 안 만들었다

`zings`는 SELECT 정책만 있었는데, `diary_reactions`는 **RLS만 켜고 정책이 0개**다. 정책이 없으면 클라이언트는 아무것도 못 읽고 못 쓴다. 대신:

- `get_match_diaries(partner)` — 매칭 확인 후 양쪽 일기 + 반응을 한 번에 돌려줌
- `react_to_diary(diary, emoji)` — 매칭 상대 일기인지, 내 일기가 아닌지 확인 후 저장

읽기도 함수로만 하면 "매칭된 두 사람만 서로의 반응을 본다"는 규칙을 정책 SQL로 복잡하게 쓸 필요가 없다. 조회와 권한 확인이 한 함수에 있어서 읽기도 쉬움.

### 4. 우회 시도 결과

앱 화면이 아니라 Supabase API를 직접 호출해서 규칙을 깨보려고 했다. 전부 막힘.

| 시도 | 결과 |
|---|---|
| 내 일기에 반응 | "내 일기에는 반응할 수 없어요." |
| 매칭 안 된 사람 일기에 반응 | "매칭된 상대의 일기에만 반응할 수 있어요." |
| 정해진 5개 외 이모지 | check 제약 위반 |
| 매칭 안 된 사람 교환일기 조회 | "매칭된 상대의 일기만 볼 수 있어요." |
| 반응 테이블 직접 조회 | 빈 배열 (정책 없음) |
| 내부 함수 `is_matched` 호출 | permission denied |

화면 검증: UI테스트 계정으로 B의 일기에 ❤️ → 😂 → 취소 → 👏, B 계정으로 로그인하면 자기 일기 아래 "UI테스트님의 반응 👏".

### 5. 네비게이션 구조 변경

교환일기는 탭 안이 아니라 **탭 위에 쌓이는 스택 화면**으로 넣었다.

```
MainNavigator (스택)
 ├─ Tabs     (홈 / 일기 쓰기 / 매칭)
 └─ Partner  (교환일기)
```

상세 화면에서는 하단 탭이 사라지고 뒤로가기가 생긴다. 앞으로 채팅도 같은 자리에 추가하면 됨.
