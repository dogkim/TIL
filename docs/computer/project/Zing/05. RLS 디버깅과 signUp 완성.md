### 디버깅 과정 요약

1. **첫 번째 원인**: `users` 테이블에 INSERT 정책 자체가 없었음 → 정책 생성
2. **두 번째 원인(진짜 원인)**: 정책을 만들었는데도 계속 403 → SQL Editor로 직접 정책 내용·세션·`auth.uid()` 값까지 다 확인했지만 전부 정상 → 정책 조건을 임시로 `true`(무조건 허용)로 풀어봐도 여전히 막힘 → **`.insert().select()`에서 `.select()`(조회) 부분에 필요한 SELECT 정책이 없었던 것이 진짜 원인**이었음. INSERT 자체는 처음부터 성공하고 있었고, 결과를 돌려주는 단계에서 막히면서 INSERT 정책 위반과 동일한 에러 메시지가 떠서 계속 엉뚱한 곳을 의심했음.
3. **덤으로 발견한 버그**: `gender` 컬럼이 실수로 NOT NULL로 생성되어 있었음 (원래 선택 항목이어야 함) → nullable로 수정

### 최종 적용한 수정 3가지

1. `users` INSERT 정책: `with check (auth.uid() = id)`
2. `users` SELECT 정책 신규 추가: `using (auth.uid() = id)` — "Users can view own profile"
3. `gender` 컬럼 `NOT NULL` → nullable로 변경

자세한 정책 내용은 [기능명세서.md](기능명세서)의 "RLS 정책" 섹션 참고.

### 배운 것 (일반화된 교훈)

- Supabase RLS는 **동작(SELECT/INSERT/UPDATE/DELETE)마다 독립적으로 정책이 필요**함. 하나라도 빠지면 그 동작만 막히는데, 에러 메시지가 다른 동작 것과 똑같아서 원인 착각하기 쉬움.
- `.insert(...).select()`처럼 여러 동작을 체이닝하면, 필요한 정책도 그만큼 늘어남 — 이건 초보만 겪는 게 아니라 Supabase 쓰는 개발자들이 흔히 걸리는 함정.
- UI(Table Editor)로 원인이 안 보이면, SQL Editor로 시스템 테이블(`pg_policies`, `information_schema.columns`) 직접 조회하고, `set local role` / `set_config`로 실제 요청 컨텍스트를 재현해보는 게 표준 디버깅 절차.
- 보안을 느슨하게 만드는 시도(정책을 `true`로 푸는 것 등)는 도구가 자동으로 막아주기도 함 — 이런 임시 테스트가 필요하면 사람이 직접 판단해서 진행해야 함.
