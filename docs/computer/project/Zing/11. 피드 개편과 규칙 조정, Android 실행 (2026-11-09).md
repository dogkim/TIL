### 1. Android에서 처음 실행 — SDK 버전 문제

Expo Go로 폰에서 열었더니 "Project is incompatible with this version of Expo Go" 에러.

- 원인: Play 스토어의 Expo Go는 **항상 최신 SDK(58)만** 지원하는데, 프로젝트는 57.
- 선택지: 옛날 Expo Go APK를 따로 설치 vs 프로젝트를 58로 올리기
- **프로젝트를 올림.** 팀원도 스토어에서 받으면 최신이라 같은 문제를 겪기 때문. `npx expo install expo@^58` → `npx expo install --fix`로 관련 라이브러리 버전 맞춤 → `expo-doctor` 20/20 통과.

연결 원리: PC의 Metro 서버(8081)가 코드를 JS 번들로 묶어주고, 폰의 Expo Go가 같은 와이파이로 `exp://<PC IP>:8081`에서 받아 실행. 화면은 웹뷰가 아니라 진짜 Android UI로 그려짐. 데이터(Supabase)는 PC를 거치지 않고 폰이 직접 통신.

### 4. 피드 — 한 장씩, 넘기면 끝

처음엔 목록(FlatList)을 화면 높이로 끊어서 넘기는 방식으로 만들었는데, 써보니 요구가 더 분명해졌다: **"한 번 넘긴 건 다시 올려서 못 보게, 랜덤으로도 다시 안 나오게. 지금은 3개 뜨고 새로고침하는 식이잖아."**

그래서 구조를 바꿨다.

- **목록이 아니라 카드 한 장.** `PanResponder` + `Animated`로 위로 밀면 카드가 날아가고 다음 카드가 올라옴. 아래로 밀면 살짝 끌리다 제자리로 (이전 카드가 애초에 없음).
- **넘긴 일기 DB 기록** (`diary_views` 테이블, `mark_diary_seen`). 화면에 "보여준 것"이 아니라 "넘긴 것"만 기록 — 보다가 앱을 닫으면 그 카드부터 다시 나옴.
- **랜덤은 DB에서** (`get_feed`, `order by random()`). 전에는 최신 100개를 받아 앱에서 섞었다. 이제 DB가 안 넘긴 일기만 골라서 10장씩 줌. 남은 카드가 3장 이하가 되면 미리 다음 10장 → 끊김 없음.
- **이미 받아둔 카드는 다시 안 받게** `exclude_ids`로 전달. 넘긴 직후 DB 기록이 끝나기 전에 다음 묶음을 요청하는 경우를 대비해 이번 세션에 넘긴 id도 같이 보냄.
- 덤으로 **절반 공개 보안이 조금 나아짐**: `get_feed`가 본문 앞 절반만 돌려줘서, 피드 응답에는 전문이 아예 없다. (단 `diaries` 테이블 직접 조회로는 아직 전문이 보임 — 남은 과제)

검증 (테스트 계정 C, D):
- C가 D 일기에 ❤️ → D의 "내 일기"에 "❤️ 1"
- 터치로 위로 밀면 0.8초 안에 다음 카드, 넘긴 수만큼 `diary_views`에 기록
- 새로고침해도 넘긴 일기는 다시 안 나옴

### 5. Supabase MCP — 이제 SQL을 붙여넣지 않는다

지금까지는 AI가 SQL 파일을 쓰면 내가 대시보드 SQL Editor에 붙여넣어 실행했다. 이번에 **Supabase 공식 MCP**를 Claude Code에 연결해서 AI가 직접 적용하게 했다.

- 방법 비교: CLI(`supabase link`)는 DB 비밀번호 입력이 필요하고 할 수 있는 게 마이그레이션 적용 정도. MCP는 브라우저에서 승인 한 번이면 되고 SQL 실행·테이블 조회·로그·보안 점검까지 가능 → MCP 선택.
- 범위는 Zing 프로젝트 하나로 제한 (`project_ref`를 주소에 고정).
- 첫 시도는 연결 타임아웃 — **무료 플랜이 7일 넘게 안 쓰면 자동 일시정지**돼 있었다. 대시보드에서 Restore.
- 두 번째 시도는 "Migration was declined" — 승인 없이 실행되게 설정했는데도 거절됨. 원인은 SQL 안의 `drop function` 줄. Supabase MCP가 **삭제가 들어간 문장은 따로 확인을 요구**하는데 그 확인 창을 띄울 수 없어 자동 거절된 것. 새로 만드는 함수라 `drop`이 필요 없어서 빼고 `create or replace`만으로 적용 → 성공.
- 적용 후 보안 점검(`get_advisors`)도 돌림. 대부분 의도한 설계(정책 없는 테이블, 로그인 유저가 부르는 `security definer` 함수). 확인 필요한 건 우리가 안 만든 `rls_auto_enable()` 함수를 비로그인 사용자도 호출 가능하다는 것 1건.

### 6. 기타 결정

- **AWS로 옮길까?** → 안 옮김. Supabase가 해주는 로그인·자동 API·권한 규칙을 AWS에서는 전부 직접 조립해야 하고, 사용자 적을 땐 오히려 비쌈. Supabase도 Postgres라 나중에 옮길 수 있고, 규칙을 DB 함수에 모아둬서 SQL은 대부분 재사용 가능.
- **지인끼리 쓰는 앱으로?** → 안 함. 지인용 교환일기 앱은 이미 있음(다이어링 등). Zing의 자리는 "모르는 외국인과의 교환일기". 친구 초대는 초기 사용자 확보용 보조 기능으로 검토.
