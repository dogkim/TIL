### `diaries` RLS 정책 4개

| 정책 | 명령 | 조건 |
|---|---|---|
| Users can insert own diaries | INSERT | `with check (auth.uid() = author_id)` |
| Authenticated users can view diaries | SELECT | `using (true)` — 로그인한 사람은 누구나 조회 가능 (피드 기능 때문에, 나중에 조건 추가 가능) |
| Users can update own diaries | UPDATE | `using`/`with check` 둘 다 `auth.uid() = author_id` |
| Users can delete own diaries | DELETE | `using (auth.uid() = author_id)` |

> USING과 WITH CHECK의 차이: USING은 "어떤 기존 row를 건드릴 수 있는지"(수정/삭제 대상 필터), WITH CHECK는 "수정한 결과가 조건을 만족하는지"(결과 검증). INSERT는 WITH CHECK만, SELECT/DELETE는 USING만, UPDATE는 둘 다 필요.

### `createDiary` 테스트 중 발견한 스키마 버그 2개

1. **`id` 컬럼이 `bigint`(정수)로 되어있었음** — 원래 `uuid`여야 함. `users`/`diaries` 테이블 초기 생성 때 `author_id`/`id` 컬럼 실수를 고치던 과정에서 잘못 남은 것으로 추정.
2. **`update_at`** — `updated_at`이어야 하는데 오타.

**수정 SQL** (테스트 데이터라 truncate 후 재생성 — 이 작업은 destructive라 Claude가 직접 실행 못 하고 사용자가 SQL Editor에서 직접 실행):
```sql
truncate table public.diaries;
alter table public.diaries drop column id;
alter table public.diaries add column id uuid primary key default gen_random_uuid();
alter table public.diaries rename column update_at to updated_at;
```

> **적용 완료 (2026-09-20)** — 재테스트에서 `id`가 `1b8fa8b7-e97d-4735-b5b7-f91c28383b88` 형태의 uuid로, `updated_at` 필드명도 정상으로 확인됨.

### 배운 것

- **`.insert().select()`는 INSERT+SELECT 정책 둘 다 필요** (이전 노트에서 배운 것, `diaries`에도 동일 적용해서 이번엔 미리 챙김)
- 테이블 만들 때 컬럼 타입/이름은 만들자마자 `information_schema.columns`로 한 번 검증하는 습관이 필요함 — 실제로 insert 결과를 받아보고 나서야(`id`가 숫자로 옴) 타입 문제를 알아챔

### `updated_at` 자동 갱신 트리거 추가

`updateDiary`가 `content`/`char_count`만 바꾸고 `updated_at`은 안 건드려서 계속 `null`이던 문제 — DB 트리거로 해결.

```sql
create or replace function public.set_updated_at()
returns trigger as $$
begin
  new.updated_at = now();
  return new;
end;
$$ language plpgsql;

create trigger set_diaries_updated_at
before update on public.diaries
for each row
execute function public.set_updated_at();
```

- **왜 코드(`updateDiary` 함수)가 아니라 트리거로 처리했나**: 모든 수정 경로(우리 앱, SQL Editor 등)에서 빠짐없이 적용되게 하려면 DB가 강제하는 게 안전 — 사람이 매번 `updated_at` 챙겨야 하는 방식보다 실무에서 훨씬 흔한 패턴.
- **`new`/`old`**: 트리거 함수에서만 쓸 수 있는 특수 변수. 파라미터로 선언 안 해도 Postgres가 자동으로 채워서 넘겨줌 (`new` = 저장될 값, `old` = 저장 전 값).
- **`before update`인 이유**: 저장되는 값 자체를 바꿔야 하므로 저장 전(Before)에 실행돼야 함. After면 이미 저장 끝난 뒤라 값 수정이 반영 안 됨.
- 실제 테스트로 `updated_at`이 정상 타임스탬프로 채워지는 것 확인 완료.
