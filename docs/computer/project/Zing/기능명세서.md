# Zing 기능 명세서

병렬 작업(백엔드/프론트) 시 서로 안 부딪히기 위한 기준 문서. 항목이 바뀌면 여기부터 업데이트하고, 코드는 그 기준을 따라간다.

## 1. 화면 목록

| 화면 | 설명 |
|---|---|
| 회원가입 | 계정 생성, 성별 비공개(자율 선택) |
| 로그인 | 이메일+비밀번호 로그인 |
| 일기 작성 | 200~600자 검증 |
| 피드 | 랜덤 일기 넘겨보기, 징 보내기 |
| 매칭 목록 | 상호 징 성사된 상대 목록 |
| 상대방 일기 상세 | 매칭된 상대 일기, 반응/댓글 |
| 프로필 | 내 정보 관리 |
| 채팅 | 제한적 소통 (로드맵 마지막 단계) |
| 알림 | 매칭 성사/반응 등 이벤트 |

(화면별 와이어프레임은 Figma 참고 — 링크 추가 예정)

### 화면 흐름 (2026-10-02 추가)

```
회원가입 ──┐
          ├──> 로그인 ──> 피드(홈) ──┬──> 일기 작성
          │                        ├──> 상대방 일기 상세 ──> (징 보내기)
          │                        ├──> 매칭 목록 ──> 채팅
          │                        ├──> 프로필
          │                        └──> 알림
          └──────────────────────────┘
```

- 회원가입/로그인 → 피드가 시작점. 피드에서 다른 화면들로 분기.
- 채팅은 매칭 목록에서 상대 선택 후 진입 (매칭 안 된 상대랑은 채팅 불가).
- 일기 작성은 피드에서 바로 진입 (탭 또는 버튼).

## 2. 데이터 모델 (테이블 스키마)

> 아래는 초안. 실제 Supabase 테이블 만들 때 이 표부터 채우고 시작.

### `users`
| 필드                  | 타입           | 설명                                           |
| ------------------- | ------------ | -------------------------------------------- |
| id                  | uuid         | PK, `auth.users.id` 참조 FK (2026-09-19, 대시보드에서 수동 설정, ON DELETE CASCADE — Auth 계정 삭제 시 프로필도 자동 삭제됨) |
| nickname            | text         | 화면에 보여줄 이름 (실명 아님)                           |
| gender              | text \| null | `'male'` \| `'female'` \| `null`(비공개, 자율 선택) |
| is_exchange_student | boolean      | 교환학생 여부 — 매칭/번역 방향 결정에 필요                    |
| nationality         | text         | 국적, 필수 — 매칭 상대의 문화적 배경을 아는 것이 서비스 핵심 가치라 비공개 옵션 없음(성별과 다름) |
| preferred_language  | text         | 일기 작성/번역 기준 언어 (예: `'ko'`, `'en'`)           |

| created_at          | timestamp    | 가입일                                          |

### `diaries`
| 필드 | 타입 | 설명 |
|---|---|---|
| id | uuid | PK |
| author_id | uuid | FK → `users.id` |
| content | text | 200~600자 검증 (프론트+DB 양쪽에서 체크) |
| char_count | int | `content` 글자 수 (검증/표시용으로 별도 저장) |
| created_at | timestamp | 작성일 |
| updated_at | timestamp \| null | 수정 시 갱신 |

> **미정**: "매칭 전 절반만 공개" 로직을 위한 필드는 아직 안 넣음 — 글자 수 기준인지 문단 기준인지(09-03 노트 미정 항목) 정해지면 그때 `public_preview` 같은 필드 또는 앱 로직(예: `content.slice(0, N)`)으로 처리할지 결정.

> **[x] 확정 (2026-10-02): 일기 하루 1개 제한.** 단계적 소통 해금(섹션 4)을 "매칭 이후 작성한 일기 개수"로 판단하기로 하면서 같이 필요해진 규칙 — 제한 없으면 한 번에 여러 개 몰아 써서 해금 단계를 부정하게 빨리 통과할 수 있음. `createDiary`에서 "오늘 날짜로 이미 작성한 일기가 있는지" 체크 후 있으면 에러 리턴하도록 구현 예정 (아직 코드 미반영).

### RLS 정책 (2026-09-19)

`users` 테이블 실제 동작 확인 중, `signUp` 테스트가 계속 403으로 막힌 문제를 디버깅해서 찾은 결론.

- `Users can insert own profile` — INSERT, `to authenticated`, `with check (auth.uid() = id)`
- `Users can view own profile` — SELECT, `to authenticated`, `using (auth.uid() = id)`

> **중요 교훈**: `.insert(...).select()`처럼 insert 후 결과를 바로 조회하는 코드는 **INSERT 정책뿐 아니라 SELECT 정책도 있어야** 동작한다. SELECT 정책이 없으면 INSERT 자체는 성공해도, 결과를 돌려주는 단계(`RETURNING`)에서 막히면서 **INSERT 정책 위반과 똑같은 403/RLS 에러 메시지**가 떠서 원인 파악이 헷갈리기 쉽다. 앞으로 테이블 만들 때마다 CRUD로 실제 쓰는 동작(insert, select, update, delete) 각각에 맞는 정책을 다 챙겨야 함 — `diaries` 등 다른 테이블도 마찬가지로 필요.

### `zings` (매칭)
| 필드 | 타입 | 설명 |
|---|---|---|
| id | uuid | PK |
| sender_id | uuid | FK → `users.id`, 징을 보낸 사람 |
| receiver_id | uuid | FK → `users.id`, 징을 받은 사람 |
| created_at | timestamp | 징 보낸 시각 |
| matched_at | timestamp \| null | 상호 성사 시각 (양쪽 다 보냈을 때 채워짐, null이면 아직 짝사랑 상태) |

> 동시 매칭 인원 상한(기본 3명 + 4단계 도달 매칭당 +1명, 섹션 4 참고) 체크는 `sendZing` 함수 안에서 구현 예정 (아직 `zings` 테이블/함수 자체가 안 만들어짐).

## 4. 정책/제약 규칙 (미정 항목 — 확정되면 여기 기록)

- [x] **동시 매칭 인원 상한 — 확정 (2026-10-02)**: 기본 3명 + **4단계(자유 채팅) 도달한 매칭마다 +1명**. 관계를 깊게 만들수록 새 매칭 여유가 늘어나는 구조. (무료/유료 세부 — 섹션 5 BM 참고, 기본 3이 무료 기준치)
- [x] **단계적 소통 해금 규칙 — 구조/수치 확정 (1~4단계), 5단계는 계획만** (2026-10-02)

  **설계 원칙**
  - 왜 이 기능이 필요한가: "교환일기 앱" 정체성(비동기·글쓰기 기반)을 지키면서도 사용자의 소통 니즈를 채워주기 위한 절충안.
  - **"기능 진화"가 아니라 "점진적 추가"**: 다음 단계가 열려도 이전 단계 기능은 없어지지 않고 계속 쌓임 (반응은 4단계 가서도 계속 가능).
  - **제한 자체가 즐거움**: 짧은 글자수 제한(5자 등)은 "불편해서 참는 것"이 아니라, 트위터·식스워드 스토리처럼 "틀 안에서 압축해서 표현하는 재미"로 설계. 그래서 단계가 올라가도 이전 단계의 제한된 소통 방식을 억지로 없애지 않음.
  - 왜 앱 안에 머물게 하는가(카톡 등으로 이탈 방지 유인): ① 번역(언어 장벽 해소), ② 앱만의 구조화된 질문-답변 게임 — 카톡엔 없는 두 가지 가치를 마지막 단계까지 유지.

  **단계표**

  | 단계 | 추가되는 것 | 질문 출처 | 질문 길이 | 답변 길이 |
  |---|---|---|---|---|
  | 1 | 반응(이모지) | — | — | — |
  | 2 | + 질문-답변 | 앱이 매일 제공 | — | 5자 |
  | 3 | + 질문-답변(서로 작성) | 유저가 직접 작성 | 7자 | 질문자가 선택: 5자 / 20자 / 100자 (공백 포함) |
  | 4 | + 자유 채팅 | 틀 없음 | — | 제한 없음 (번역 계속 지원) |
  | 5 (계획만, 1차 범위 제외) | + 사진 공유 | — | — | — |

  - 3단계의 핵심 차이는 글자수가 아니라 **"누가 질문을 만드는지"**(앱 → 유저 자신).
  - **질문자가 답변 글자수를 직접 선택 가능** (2026-10-02 추가): 질문 만들 때 답변 제한을 셋 중 하나로 고름 — **5자 / 20자 / 100자**(공백 포함, 기존 `char_count` 계산 방식과 동일). 질문자가 관계 깊이를 스스로 조절하는 느낌을 주기 위함. 100자를 상한으로 둔 이유는 일기 최소 글자수(200자)·4단계(자유 채팅)와 확실히 구분되게 하려는 것 — 3단계가 "틀이 있는 소통"이라는 정체성을 유지.
  - DB 설계 시 참고: 질문마다 답변 제한값(5/20/100)을 저장할 필드 필요 — `zings`/`messages` 테이블 실제 구현 시 반영.
  - 4단계는 "질문 틀" 자체가 사라지는 게 핵심 차이 (글자수 제한 철폐는 부수 효과).
  - 5단계(사진 공유)는 Supabase Storage 등 새 인프라가 필요해 개발 비용이 커서 1차 런칭 범위에서 제외, 자유 채팅(4단계) 이후에 여유 생기면 추가.
  - 안전장치(신고/차단)는 모든 단계에 무관하게 항상 있어야 함.

  **단계 전환 기준 (초안, 조정 가능)**
  | 단계 전환 | 조건 |
  |---|---|
  | 1 → 2 | 매칭 후 **둘 다** 일기 2개 이상 작성 |
  | 2 → 3 | 매칭 후 **둘 다** 일기 4개 이상 작성 |
  | 3 → 4 | 매칭 후 **둘 다** 일기 7개 이상 작성 |

  - 날짜가 아니라 **"매칭 이후 각자 쓴 일기 개수"** 기준 — 실제 관계 활동량을 더 잘 반영하고, `diaries.author_id` + `created_at`으로 매칭 이후 작성분만 세면 돼서 구현도 어렵지 않음.
  - **"둘 다"** 조건 충족해야 다음 단계로 — 한쪽만 활발하고 한쪽이 방치하면 자연스럽게 관계가 다음 단계로 안 넘어감 (의도된 동작).
  - 개수는 초안 — 실제 적용 전 재검토 가능.

  - **전체 공개 시점**: 상호 징 성사 즉시(1단계 진입 시)

    - 가입 시 이메일 소유 확인 (Supabase Auth "Confirm email" — 개발 중 테스트 편의로 꺼뒀던 것을 **런칭 전 다시 켜야 함**)
    - 한국 학생(`isExchangeStudent: false`)은 이메일이 `.ac.kr`로 끝나는지 추가 체크 (자동 검증 가능)
    - 교환학생(`isExchangeStudent: true`)은 국가별 학교 이메일 형식이 제각각이라 도메인 자동 검증은 어려움 — 이메일 소유 확인만 적용, 완전한 소속 검증은 범위 밖
  - **검증 안 하는 것 — 성별/나이 등**: 이메일 인증으로는 애초에 증명 불가능한 영역. 정부 ID 기반 검증은 국가마다 형식이 다르고 민감정보 처리 부담(법적 책임)이 커서 범위 밖으로 판단. 자진 신고 유지 + 신고/차단 기능으로 사후 대응 (에브리타임처럼 서류 업로드 + 사람이 수동 검수하는 방식은, 가입자 늘어날수록 운영 부담이 커서 1인/소규모 팀엔 비현실적이라 채택 안 함).
  - 결론: **"학교 소속"만 최소한으로 검증하고, 그 외 신원 요소는 자진 신고 + 사후 신고 체계로 간다.**

## 5. 비즈니스 모델 (BM) — 방향 확정 (2026-10-02), 세부 수치 미정

실제 런칭을 염두에 두고 있어서 수익 구조도 고려하되, **매칭/소통의 핵심 경험 자체는 유료화하지 않는다**는 원칙으로 간다. (2026-10-02 수정: 번역은 전면 무료 원칙에서 "일기 번역은 무료 / 채팅 번역은 사용량 제한"으로 세분화)

### 전략: 핵심 무료 + 부가 기능 유료, 초기엔 전부 무료로 런칭

1. **항상 무료**: 일기 작성/조회, **일기 번역**, 소통 단계 해금 1~4단계 진입 자체 — 유료화 대상 아님
2. **유료화 후보 — 부가/편의 기능**:
   - **채팅 번역**: 무료는 하루 N회까지, 초과분은 유료 (정확한 횟수 미정)
     - 왜 채팅만: 일기 번역은 "매칭 여부를 결정하는 핵심 진입 경험"이라 막으면 진입장벽이 생김. 채팅 번역은 이미 4단계(둘 다 일기 7개 이상)까지 온 고관여 사용자 대상이라 상대적으로 수용 가능하고, 실시간 대화라 호출량도 일기보다 훨씬 많아서 비용 통제 필요성도 더 큼.
     - 채팅 자체(글 주고받기)는 계속 무료 — 제한되는 건 "자동 번역 기능"만. 번역 없이 원문으로 채팅하는 건 무제한.
   - **동시 매칭 인원 상한 확장권** (무료 기본 3명 + 4단계 도달 매칭당 +1명 외 추가 확장)
   - **하루 징 전송 횟수 확장**
   - **단계 스킵권**: 일기 개수 기준 대기를 돈으로 스킵 (예: 2단계 진입까지 기다리는 대신 바로 시작) — 핵심 기능 자체를 막는 게 아니라 "대기 시간을 돈으로 사는" 성격이라 원칙과 덜 충돌한다고 판단
   - **일기 최대 글자수 확장**: 무료 600자 → 유료 1200자(2배). **최소 글자수(200자)는 유료로도 완화 안 함** — 최소치를 낮추면 "성의 있는 글쓰기"라는 서비스 정체성과 직접 충돌해서 제외, 최대치만 여유를 주는 쪽으로 한정.
     - 구현은 결제 시스템 자체가 아직 없어 보류 — `users` 테이블에 유료 여부 필드 추가 + `createDiary`/`updateDiary`의 글자수 검증 로직에서 분기 필요 (결제 기능 만들 때 같이 작업)
   - 프로필 꾸미기, 피드 노출 우선순위 등
3. **런칭 초기엔 위 부가 기능도 전부 무료로 오픈** (사용자 확보 우선) — 단, "런칭 이벤트 기간 무료, 이후 일부 유료 전환 예정"이라고 처음부터 공지해서 나중에 바뀌어도 신뢰 안 깨지게 함
4. **초기 가입자 혜택 유지 고려**: 서비스 안정화 후 유료 전환 시, 런칭 초기 가입자는 혜택 계속 유지하는 방안 검토

### 참고 — 비용 구조상 자연스러운 안전장치
번역 API는 매칭된 상대와 소통할 때만 쓰이므로, "동시 매칭 인원 상한" 정책 자체가 번역 API 사용량(=비용)을 어느 정도 자연스럽게 제어해줌. 채팅 번역 사용량 제한(위 항목)과 별개로, 매칭 상한 자체도 비용 억제에 기여.
